# Управление нодами

Весь код — `server/src/services/provision.service.ts`, SSH — `ssh.service.ts`, скрипт развёртывания —
`server/src/scripts/deploy-awg.sh`.

## Модель контейнера

Нода описывается полями сервера `container_name`, `iface`, `conf_path`, `awg_tool`, `managed_by`.

| Тип | container_name | iface | conf_path | awg_tool | Где конфиг |
|---|---|---|---|---|---|
| Контейнер панели (`dementia`) | `amnezia-awg` | `awg0` | `/opt/amnezia/awg/awg0.conf` | `awg` | На хосте, смонтирован в контейнер |
| Приложение Amnezia, AWG (`amnezia`) | `amnezia-awg2` или `amnezia-awg` | `awg0` | `/opt/amnezia/awg/awg0.conf` | `awg` | Внутри контейнера |
| Приложение Amnezia, legacy (`amnezia`) | `amnezia-awg` | `wg0` | `/opt/amnezia/awg/wg0.conf` | `wg` | Внутри контейнера |

Конфиг всегда пишется через `docker exec -i <container> sh -c 'cat > conf.new && mv conf.new conf'` — это работает
для обоих случаев. Не используйте SFTP и `/tmp` на хосте (раньше там оставались приватные ключи).

Для не-root SSH-пользователя команды выполняются через `sudo -n` (нужен NOPASSWD).

## Очередь операций

`runExclusive(serverId, fn)` — все операции одной ноды выполняются последовательно. `requestSync` и `requestApply`
объединяют повторные запросы, пока операция не началась (`pendingSync`, `pendingApply`): двойной клик по «Применить»
не перезапустит контейнер дважды. Установка помечается в `installing` и не может запускаться параллельно.

## Установка (`installServer` → `doInstall`)

0. **Проверка до любых изменений** (`findForeignContainer`): перед установкой нода сканируется. Если там работает контейнер
   приложения Amnezia, который скрипт удалил бы (имя `amnezia-awg` либо тот же UDP-порт) и который ещё не подключён к этому
   серверу, установка возвращает ошибку с подсказкой «Сканировать», статус сервера не меняется, скрипт не отправляется. Если
   сервер проверить нельзя (SSH, sudo), установка тоже не начинается (статус `error`).
1. Генерируются (если нет) ключ сервера и PSK; публичный ключ вычисляется локально (`derivePublicKey`).
2. Полный конфиг (интерфейс + все активные пиры из БД) кодируется в base64 и передаётся в `deploy-awg.sh` вместе с
   `AWG_PORT`, `AWG_NETWORK` (адрес сети для NAT), `AWG_IMAGE` (`amneziavpn/amneziawg-go:latest`),
   `REPLACE_CONTAINER` (имя чужого контейнера, который нужно удалить), `PANEL_IP` (из `SSH_CLIENT`, для `ignoreip`).
3. Скрипт передаётся **через stdin** (`bash -c 'script=$(cat); exec bash -c "$script"'`) и не сохраняется на диске.
4. Скрипт: проверка x86_64 → Docker (apt / репозиторий Docker CE для EL / get.docker.com) → `ip_forward` →
   `docker pull` → `awg0.conf` и `demension.env` → `start.sh` (POSIX sh, идемпотентные правила iptables, NAT по
   `AWG_NETWORK`, корректная обработка SIGTERM) → контейнер с `--cap-add NET_ADMIN --device /dev/net/tun` →
   открытие UDP-порта в ufw/firewalld → fail2ban (порт из `sshd -T`, backend auto/systemd, `ignoreip` с IP панели) →
   ожидание интерфейса до 20 с.
5. Успех определяется по маркеру `---DEMENTIA_OK---` и коду 0. После успеха сервер становится `managed_by =
   dementia`, `deployed_port = awg_port`.

Переустановка **сохраняет клиентов** (они есть в конфиге из БД). Подключённый ранее контейнер Amnezia заменяется
контейнером панели с теми же ключами — выданные конфиги продолжают работать.

## Обновление образов AmneziaWG

`services/node-update.service.ts`, `scripts/update-awg.sh`, API `/api/node-updates`, карточка «Обновления AmneziaWG» в разделе «Серверы».

- Проверка раз в сутки: `docker pull amneziavpn/amneziawg-go:latest`, сравнение immutable ID образа (`sha256:…`) с `.Image` работающего контейнера. Одного `docker restart` недостаточно. Скачивание не останавливает VPN.
- По умолчанию только проверка и уведомление. «Обновить все» запускает доступные обновления по очереди. Автообновление включается явно; окно — выбранный час UTC (по умолчанию 03:00–04:00). После окончания окна новая нода не запускается, уже начатая операция завершается. Настройки: `node_auto_update`, `node_update_hour` в `settings`; состояние — `node_updates` (миграция v13).
- Только работающие ноды панели (`managed_by = demension`) со стандартными полями контейнера и применёнными портом и конфигом. Контейнеры приложения Amnezia, ноды партнёров, offline-ноды и ноды с `needs_sync`/`needs_apply` пропускаются. Для импортированной ноды сначала нужна явная переустановка в контейнер панели.
- `ProvisionService.maintainContainer` использует `runExclusive` и приостанавливает опрос на время замены. Проверка и обновление не пересекаются с синхронизацией, применением или переустановкой одной ноды. Пакеты и планировщик имеют общий замок. Перенос панели приостанавливает новые операции.
- Удалённая команда ограничена `timeout` (18 минут, TERM и 30 секунд на откат до KILL); SSH ждёт 20 минут. Удалённая операция не должна продолжать замену контейнера после освобождения очереди по таймауту SSH.
- Обновление **не генерирует конфиг и не пишет в таблицы клиентов/подписок**. Перед остановкой сравниваются ключ интерфейса и порт, ключи/PSK/IP/keepalive всех работающих пиров с файлом конфигурации. Несохранённые ручные изменения блокируют замену. Сохраняются также импортированные и партнёрские пиры; отключённые клиенты остаются в БД.
- Старому контейнеру отключается автозапуск, он переименовывается в `<container>-dementia-update-backup` и останавливается. Новый создаётся из скачанного **ID** со стандартными настройками запуска панели и смонтированным каталогом. Конфиги, ключи, скрипт запуска и окружение на диске не изменяются. Проверяется совпадение интерфейса и пиров (`awg show dump`, без счётчиков, roaming Endpoint и рукопожатий); резервный контейнер удаляется только после успеха.
- При сбое EXIT/HUP/INT/TERM-обработчик удаляет новый контейнер, возвращает прежнее имя и `--restart always`, запускает старый контейнер и проверяет пиры. Если осталось резервное имя после аварийного завершения (например, отключения питания), следующая операция отказывается что-либо удалять: администратору нужно проверить ноду и восстановить резервный контейнер. Откат после SIGKILL/отключения питания не гарантируется.
- После ошибки проверка и автоматическая попытка ограничены сутками; вручную можно повторить раньше. `node.update_available`, `node.updated`, `node.update_failed`, `node.update_check_failed` попадают в журнал и Telegram согласно его настройкам (`notify_info` для успешных событий). SSH-вывод и ключи не возвращаются в API и журнал.
- Проверка интерфейса и пиров подтверждает восстановление конфигурации, но не заменяет сквозной тест клиентского трафика. Пересоздание кратковременно прерывает VPN. Обновление образа не меняет версию параметров протокола 1.x/3.x.

## Синхронизация пиров (`requestSync` → `doSync`)

Пишет полный конфиг и выполняет `awg-quick strip … | awg syncconf <iface>` внутри контейнера (без разрыва соединений).
Если на сервере `needs_apply`, вместо этого выполняется применение. При ошибке `needs_sync` остаётся, и фоновый опрос
повторит попытку, когда нода ответит. Для нод партнёра `requestSync` вызывает `FederationClient.requestSync`.

## Применение параметров (`requestApply` → `doApply`)

`syncconf` не меняет обфускацию, поэтому: конфиг + `docker restart <container>`. Для контейнера панели также
перезаписывается `demension.env`. Если `deployed_port !== awg_port` — полная переустановка. Вызывается при изменении
параметров (PUT, randomize). Одновременные запросы объединяются в один перезапуск (`pendingApply`).

PUT и randomize ждут результата (`applyOrRollback` в routes/servers.ts). Если применить не удалось (нода недоступна,
установка отказалась трогать чужой контейнер, ошибка скрипта), изменённые порт, подсеть и параметры возвращаются в БД к
прежним значениям, а API отвечает 502. Иначе подписки раздавали бы клиентам порт и параметры, которых на ноде нет, и VPN
пропал бы у всех. `needs_apply` при откате остаётся: нода могла получить часть изменений, и фоновый опрос приведёт её к
прежним параметрам. Значения, которые успели изменить ещё раз, пока шло применение, не откатываются.

Переход 1.x → 3.x (`POST /servers/:id/upgrade-protocol`): новые параметры (I1–I5 и `extra_params` сохраняются) +
`requestReinstall` (свежий образ). При неудаче параметры откатываются, чтобы подписки не раздавали несовместимые конфиги.

## Сканирование и подключение без переустановки (`scanAndAdopt`)

Вызывается автоматически после добавления сервера (клиент `App.handleServerAdded`), кнопкой «Сканировать» и при
импорте ключей AmneziaVPN.

1. `detectContainers`: одной SSH-командой перебирает `docker ps -a`, берёт контейнеры, у которых имя или образ
   содержит `amnezia-awg`/`amneziawg`; для работающих читает `awg0.conf` или `wg0.conf`, определяет утилиту
   (`awg`/`wg`), читает `clientsTable` (имена клиентов Amnezia), отмечает контейнер панели (есть `demension.env`).
   Вывод размечен маркерами `---CONTAINER/---CONF/---TOOL/---CLIENTS/---DEMENTIA` (`parseScanOutput`).
2. Выбирается контейнер панели, иначе первый работающий с конфигом.
3. `parseServerConfig` извлекает ключ, адрес, порт, параметры (версия 3, если есть S3/S4/HPK/диапазоны H) и пиры.
4. `adoptConfig` в транзакции: обновляет сервер фактическими значениями (порт, подсеть, ключи, параметры, поля
   контейнера, `deployed_port`, статус `online`) и добавляет пиры как клиентов `external = 1` (пропуская известные
   ключи и занятые IP).

**Важно:** после подключения контейнера Amnezia клиентами нужно управлять только из панели — изменения, сделанные в
приложении Amnezia, будут перезаписаны при синхронизации (инвариант 10 в AGENTS.md).

## Мониторинг (`fetchServerStats`, `applyDump`)

`docker exec <container> <tool> show <iface> dump` раз в 30 с. Ненулевой код или ошибка SSH → `fail_count + 1`,
после 3 подряд — `offline`. Несовпадение ключа хоста → `error` без повторов. При успехе — `online`, и если были
`needs_sync`/`needs_apply` или нода вернулась из offline, запускается досинхронизация. Трафик накапливается дельтами;
дамп применяется одной транзакцией (один коммит вместо коммита на каждого пира, без частично обновлённых клиентов).
Сброс трафика пользователя обнуляет только `total_rx`/`total_tx` — счётчики интерфейса остаются, иначе следующий опрос
вернул бы весь накопленный трафик.

Версии ПО (`fetchNodeInfo`): при опросе, если `node_info_at` пуст или старше 12 ч, отдельной командой читаются
`amneziawg-go --version`, `awg --version` (или `wg`), образ контейнера и дата его сборки. Установка и подключение
контейнера обнуляют `node_info_at`, чтобы версии перечитались сразу. Вывод с ноды разбирается `parseNodeInfo` только по
строгим форматам (значения показываются в интерфейсе). Ошибка чтения версий не меняет статус ноды. У нод партнёра версий
нет (нет SSH).

Доступность нод из других стран (заглушка на ноде и check-host.net) — отдельная необязательная функция, см. [probes.md](probes.md):
при её включении на ноду ставится второй контейнер `dementia-probe` (каталог `/opt/dementia-probe`, случайный порт TCP+UDP), контейнер
AmneziaWG он не трогает. Мосты в странах пользователей — [bridges.md](bridges.md). Перенос
панели на другой сервер не трогает ноды: SSH-ключи хостов, доступы и клиенты переезжают в БД ([migration.md](migration.md)).

## Запасные порты AmneziaWG

Код — `services/extra-ports.service.ts`, правила — `utils/extra-ports.ts`, API — `PUT /api/servers/:id/extra-ports`, интерфейс —
`NodeExtraPorts.tsx` (строка «Запасные порты» у ноды), выдача — `routes/subscription.ts`.

Блокировка часто ставится на пару «адрес:порт», а смена основного порта требует пересоздания контейнера и рвёт всех клиентов.
Запасной порт (до 4 на ноду) — правило на **хосте ноды**: UDP `нода:запасной` → DNAT → `адрес контейнера:awg_port`. AmneziaWG,
его конфигурация и контейнер не меняются и не перезапускаются; ключи и параметры обфускации те же.

- **Правила целиком из БД** (`buildPortRules`, как правила моста): своя цепочка `DEMENTIA-PORTS` в `nat`, переход в неё — первым в
  `PREROUTING` и только для пакетов на адреса самого сервера. Файл `/etc/dementia-ports/rules.sh` и служба `dementia-ports.service`
  возвращают правила после перезагрузки (без systemd — фоновая сверка панели).
- **Адрес контейнера определяется на ноде при каждом применении** (`docker inspect`): туда же ведёт правило самого Docker для
  основного порта, поэтому пересылку разрешают его же правила, а AmneziaWG видит настоящий адрес клиента. После пересоздания или
  перезапуска контейнера адрес может измениться — `doInstall`, `doApply` и обновление образа применяют правила заново из той же
  очереди (`ProvisionService.reapplyExtraPorts`).
- **Отметка применения** — `servers.extra_ports_hash` (SHA-256 правил). `ExtraPortsService.activePorts` возвращает порты, только
  если отметка соответствует текущим порту, контейнеру и списку; **в подписку попадают только они** (инвариант 28). Запись в подписке —
  `<имя> · порт N` с тем же конфигом и другим `Endpoint`, сразу после основной; при мосте в режимах `auto`/`always` (прямой адрес
  не выдаётся) запасных записей нет. В mihomo они входят в группу «Авто» ([subscriptions.md](subscriptions.md)).
- **Фоновая сверка** `ExtraPortsService.checkAll` (`statsLoop`): отметка не совпала с БД — применить заново; раз в 5 минут — проверить
  на ноде, что правила на месте и ведут на нынешний адрес контейнера, иначе отметка сбрасывается (порты пропадают из подписки до
  повторного применения). После неудачи повтор не чаще раза в 5 минут; ошибка — в `servers.extra_ports_error`.
- **Ограничения.** Только свои ноды AmneziaWG (не VLESS, не ноды партнёра; партнёрам запасные порты не передаются). Порт не может
  совпадать с основным, с портом заглушки проверки и с основным портом другой AWG-ноды на том же адресе; основной порт нельзя сменить
  на запасной. Запасные порты соседних нод одного адреса тоже не пересекаются, и основной порт новой или изменённой ноды не может
  совпасть с чужим запасным (цепочка `DEMENTIA-PORTS` стоит первой в PREROUTING и перехватила бы трафик). Внешний фаервол хостера (группа безопасности) панель не настраивает — порты нужно открыть там вручную. Мост пересылает
  только основной порт ноды.
- Сбой применения из API — 502, список возвращается к прежнему. Удаление ноды с очисткой снимает цепочку и службу.

## Удаление

`DELETE /servers/:id?teardown=1` удаляет контейнер на ноде (и `/opt/amnezia/awg` для контейнера панели), а также заглушку проверки
`dementia-probe` с `/opt/dementia-probe` и правила запасных портов (`DEMENTIA-PORTS`, `/etc/dementia-ports`). Привязки ноды к мостам удаляются каскадно, правила мостов перестраиваются фоновым опросом.
При ошибке — 502, если не передан `force=1`. Без teardown VPN на ноде продолжает работать.

## VLESS

Ноды с `protocol = 'vless'` ([vless.md](vless.md)) обслуживаются теми же методами `ProvisionService` и той же очередью; ветвление — по `nodeProtocol(server)`.

- **Установка** (`doInstallVless`): до изменений проверяется, что контейнер `dementia-xray` без метки `/opt/dementia-xray/dementia.env` не существует и TCP-порт
  не занят чужой службой. `deploy-xray.sh` (через stdin): Docker, `docker pull ghcr.io/xtls/xray-core:latest`, проверка конфига `xray run -test` до замены
  контейнера (временный файл `config.new.json`: формат Xray определяет по расширению, `config.json.new` он не читает), контейнер `--restart always --network host --user 0:0` с каталогом `/opt/dementia-xray` в `/etc/xray`, открытие TCP-порта, fail2ban, ожидание
  работающего контейнера и порта. Успех — маркер `---DEMENTIA_OK---`, затем `deployed_port = awg_port`.
- **Синхронизация и применение**: config.json пишется на хост (`umask 077`, атомарный `mv`), затем `docker restart`. Смена порта — переустановка.
- **Статистика**: `docker exec dementia-xray /usr/local/bin/xray api statsquery -s 127.0.0.1:10085 -reset`; разбор — `parseXrayStats` (строгий формат имён
  `user>>>c<id>>>>traffic>>>uplink|downlink`), uplink → `total_rx`, downlink → `total_tx`.
- **Сведения о ноде**: `xray version` и образ. Образ distroless: в контейнере нет `sh`, команды вызывают бинарник напрямую.
- **Удаление**: только контейнер `dementia-xray` и каталог `/opt/dementia-xray` (если на нём метка панели); AmneziaWG и `/opt/amnezia` не затрагиваются.
- Сканирование, обновление образов (`NodeUpdateService`) и заглушка проверки из стран для VLESS-нод не выполняются.
